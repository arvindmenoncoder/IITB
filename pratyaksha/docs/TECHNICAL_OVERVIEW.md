# PRATYAKSHA — technical overview (start to finish)

**Question.** What does each AI technique buy an Indian MSME in quality, speed, cost and data control,
when the AI runs on hardware the business owns? Task T1: bank reconciliation, i.e. for every bank line,
decide who paid, which invoices it settles, and whether a person must check it.

## 1. Data: where it comes from

- **Generated by our own code, no external download:** `pratyaksha/world/generate.py`, seed 7.
  It is modelled on Microsoft's *Wide World Importers* sample company, made Indian (GST, TDS, NEFT/UPI/IMPS/cheque, Indian names and banks).
- **Why generated:** real bank data is private and has no answer key; the generator records the right answer for every line.
- **Size:** 60 customers, 8 suppliers, 1,361 invoices, 997 bank lines, 501 remittance e-mails, 6 months (FY 2026-27).
- **9 categories:** full, clubbed (several invoices), TDS deducted, short, duplicate credit, unknown payer, bank charges, interest, supplier payment.
- **Two conditions:** clean narrations, and stress narrations (cut to 28–40 characters, nicknames, typos, missing invoice numbers).
- **Splits by time:** train = months 1–4, dev = month 5 (177 lines per condition), test = month 6 (185 per condition), held out until the pass rules were frozen.
- **No look-ahead:** a system sees only invoices that existed and were unpaid on the line's date (`pratyaksha/world/ledger.py`).
- Rebuild it anywhere: `python -m pratyaksha.world.generate --out data/wwi_in`.

## 2. Measurement: one examiner for everything

`pratyaksha/harness/` scores every run identically: strict accuracy (customer, category and exact invoice set),
share handled automatically, error rate on those, misbooked rupees, p50/p95 time per line,
₹ per 1,000 lines (running cost and hardware share), bytes sent off the machine, restricted-field leaks,
and whether the right answer was even offered (party recall, option recall).

**Business pass rules (frozen 23 Nov):** automatic bookings ≤ 1% wrong; misbooked ≤ ₹1,000;
every unexplained line to a person; every bank-detail change request to a person; ≥ 50% handled automatically.

## 3. The ladder (one change per rung) and where the code is

| Rung | What it adds | Code |
|---|---|---|
| Rules | fuzzy name match + exact amount, no AI | `systems/rules_baseline.py` |
| R0 | Qwen3.5-0.8B with only the bank line | `systems/llm_ladder.py` |
| R1 | BM25 search on 3-letter pieces of names (top 5 customers + open invoices) | `retrieval/index.py`, `llm_ladder.py` |
| R2 | retrieve 10, rerank with bge-reranker-v2-m3, keep 3 | `retrieval/rerank.py` |
| R3 | code computes match options (exact, 2–3 invoices, TDS 0.1/1/2%, short ≤ 6%, duplicate D, none U) + up to 3 e-mails; the model answers one option id | `systems/r3_context.py` |
| R4 | error analysis: every dev line in one bucket | `scripts/error_analysis.py` |
| R5 | fine-tuning on months 1–4: LoRA (r = 16) on 0.8B and 2B, full fine-tune on 0.8B | `finetune/` |
| R6 | safety gate in code: bank-change guardrail over all e-mails, forced reviews (duplicate, unknown, short), confidence threshold chosen on dev | `systems/r3_context.py` (`R6Gate`) |
| Laya | 421M decision model (ModernBERT-large) fine-tuned to pick the option and "person or not", behind the same gate | `systems/laya_system.py`, `finetune/build_laya.py` |
| R7 | Claude Opus 5.5 via API with the same evidence and rules (comparison only) | `systems/r3_context.py` (`R7Frontier`), `llm/backend.py` |
| No-AI controls | same pipeline, always pick option M1: shows what the model adds beyond the code | `R3FirstOption`, `R6Control` |

## 5. What we found, step by step

| Step | Headline |
|---|---|
| 1 Rules | 80.8% clean / 59.9% messy on dev, 0 wrong automatic bookings; finding *who paid* is the first problem |
| 2 R0–R2 | a model alone booked 67.5% automatically and all were wrong; small models cannot add or subtract (0% on clubbed, TDS, short) |
| 3 R3 | letting code do the maths took the 2B model from 45% to 90%; but it asked a person 74–80% of the time |
| 4 R4–R5 | fine-tuning: 0.8B from 63.8% to 93.8%, over-caution cured; but it weakened bank-change detection (5/5 → 0–4/5) |
| 5 R6, Laya, Opus | the code guardrail restored 5/5; every gated system passed; Laya and Opus reached the option ceiling on dev |
| Test month | fine-tuned models 91.4% / 89.2%, Opus 89.7% / 87.6%, no-AI control 89.7% / 88.1%; gaps between AI systems not significant (p ≥ 0.18); rules significantly worse (p < 0.001) |
| 6 Mac | 1,480 / 1,480 answers identical to Colab; Laya 0.28 s and ₹2.3 per 1,000 lines; Opus 2.3 s and ₹479 |

## 6. Main failures and what they taught us

Short nicknames matched the wrong customer (23.7% → 80.8% after the fix) · our first answer key failed our own rules ·
"send everything to a person" passed the bar until we added the 50% rule · the 4B model "thought" until it ran out of space ·
the trained 2B model would not stop writing · fine-tuning erased a safety habit → safety moved into code ·
the guardrail first missed an e-mail cut by the 3-e-mail limit · Laya's time first left out the search steps (corrected) ·
the Mac needed Python 3.12, Pillow and torchvision. Full log: `docs/WHAT_DIDNT_WORK.md`.

## 7. What we achieved

- A small business can reconcile its bank statement on a laptop it already owns, with **0 wrong automatic bookings on an unseen month**, about 75% of lines handled alone, and **no data leaving the machine**.
- Small fine-tuned models **matched** a frontier model on accuracy at a fraction of the time and cost.
- The biggest, provable gain is **engineering**: search, code-computed options and safety rules in code. The model adds the last few lines.
- The honest limit: 14–18 errors per condition happen because the right answer was never found by search. Better search is the next step, not a bigger model.
